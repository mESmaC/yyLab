# Per-update NVFP4 forward-weight cache candidate

This is an isolated benchmark experiment, rejected from this round's speed comparison after CUDA validation failed both full-model parity checks. No throughput result is accepted. No production files, optimizer defaults, or checkpoint/resume contracts are changed.

`benchmark_weight_cache.py --config weight-cache-b32.json --output <new-directory>` invokes the official Sprint precision benchmark. The recipe explicitly sets `experimental_weight_cache: "nvfp4_forward_per_update"`. The numerical precision remains `nvfp4_mxfp8_fast`; reports additionally identify `benchmark_variant: "nvfp4_mxfp8_fast_weight_cache_per_update"` at the top level, in each case and in precision metadata. Runtime cache metadata and the SHA256 of both executable artifact files are retained. This must be compared with a fresh process using the same baseline shape, effective batch, schedule, precision, compile mode and measurement length.

Each decoder projection keeps nonpersistent CUDA buffers for packed FP4 forward-weight codes, blocked FP8 scales and a FP32 global scale. The input embedding and output head are unchanged. Each update refreshes every cache once, then reuses those buffers for all accumulation microbatches. Activation quantization, fresh gradient quantization, and both existing MXFP8 backward GEMMs remain unchanged. The BF16 Parameter objects and straight-through backward gradients are retained. No backward weight-column cache is implemented.

Refresh uses the same TorchAO quantization and block-reordering operations, compiled into fixed-shape functions with CUDA graphs disabled. Those functions copy into stable buffers. Their first compilation occurs during benchmark warmup; every later refresh and the host validity checks occur inside `train_step` and are included in measured time. The existing CPU optimizer enqueues a caller-stream wait on its final weight-writeback stream. Refresh is queued on that same caller stream, so it observes the latest completed BF16 weights without a host-wide CUDA barrier.

Cache scope remains active through every forward/backward microbatch and the optimizer update, and invalidates in `finally`. Host checks immediately before and after each microbatch reject ordinary in-place weight changes, changed Parameter identities, storage-device/dtype changes, and invalidated scopes. `load_state_dict(assign=False)` is allowed between scopes and forces an unconditional refresh next time; loading within an active scope is rejected before the root model loads parameters. Parameter replacement, device/dtype moves after cache installation, concurrent use, stream changes, and external `.data` writes are outside this experiment. PyTorch cannot detect `.data` writes through its ordinary Parameter version counter. No version or changing generation counters enter the compiled graph.

The BF16 model must be placed and cast before cache installation. The benchmark does this after engine initialization and before the model's first lazy compiled execution. Cached buffers are registered with `persistent=False` and do not appear in `state_dict`; this is not a serialized quantized model or a supported production resume mode. A forward outside the update scope raises instead of using stale packed weights.

For the current 999,346,176-parameter shape, the cache covers 965,738,496 decoder matrix parameters: 482,869,248 packed-code bytes plus 60,456,960 blocked-scale bytes (including scale-layout padding) and 96 scalar bytes, totaling **543,326,304 bytes (0.506 GiB)**. Initialization/packing/compiler workspaces can raise the actual peak substantially beyond that retained size. The runtime receipt records actual allocated buffer bytes. More persistent GPU memory can worsen Windows memory pressure; a short timing win is insufficient without a longer confirmation and a complete passing parity suite.

Run correctness checks only when the root agent allocates the GPU:

```powershell
.venv/Scripts/python.exe -m pytest artifacts/sprint-1b-speed-20260911/test_weight_cache.py -q -s
```

Tests cover exact compiled packed bytes/scales, stable buffer addresses, parameter identity, stale-scope and mutation rejection, load-state invalidation, absent serialized cache, and matched losses/gradients/BF16 weights/FP32 CPU optimizer state over multiple updates with distinct microbatches, both eager and compiled. A failed parity or compile check rejects the candidate; no dense fallback or weakened tolerance is provided.

The root agent ran the combined candidate suite: 9 passed and 2 failed in 71.62 seconds. Six passing checks belong to the separate BF16-moment candidate. This cache's two packed-payload checks and its scope check passed, but its eager and compiled full-model parity checks failed. The preserved `cache-parity-attempt1/validation.json` is a transcribed result summary rather than a complete pytest log. The source and strict tests from that attempt are retained alongside it.

The subsequent tiny `cache-first-difference.json` diagnostic found identical initial model weights. Eager refresh matched every payload, layer output, and both losses exactly. Compiled refresh differed from eager provider packing in 45 of 24,576 QKV code bytes and 5 of 16,384 up-projection code bytes, while block/global scales matched. The first activation divergence was the QKV projection with identical inputs. Flattened versus two-dimensional cached blocked scales gave identical results, excluding that reconstruction choice as the cause. The original payload tests compared two compiled packing functions and therefore missed this eager-versus-compiled difference. Inductor's approximate-versus-round-to-nearest FP32 division is a possible mechanism, but no corrective setting or fix was executed or validated. Scope is closed for this round; all tolerances remain unchanged.
